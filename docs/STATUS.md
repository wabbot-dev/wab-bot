# Status: what is verified, how, and what is not

Read this page before you trust WAB bot with customers. Every claim in this repository is meant to carry its evidence and its limits; this page is the index. If another page says something this page contradicts, this page wins and the other page is a bug ([documentation issue](https://github.com/wabbot-dev/wab-bot/issues/new?template=documentation.yml)).

## Known limits

- Media is not downloaded (type and caption only). Templates: text and body-parameter only. No groups. No voice calls in the bridge itself.
- Escalated and taken-over chats never wake the agent; staff watch `/admin`. Lease expiry is lazy.
- Single tenant, one Durable Object (all writes serialised, one row per conversation): not for high volume. Many simultaneous messages for the **same** conversation contend on one row and can get 503 (Meta redelivers).
- Reactions are stored but neither wake the agent nor reopen the 24-hour window.
- While your agent URL is down, every further inbound message for that conversation attempts another wake POST (seen live: hundreds of attempts in a load run).
- Delivery-status webhooks (sent, delivered, read) are accepted but not persisted, except `failed` or an uncertain send.
- Cloudflare Free limits apply and can change ([CLOUDFLARE.md](CLOUDFLARE.md)); individual requests exceeded 10 ms of CPU in our runs without being terminated, which does not prove the limit is never enforced.

## Live measurements (Cloudflare Free, fake secrets, 2026-10-16)

These come from three throwaway deployments (all deleted afterwards) of **earlier revisions** of this code on a real Cloudflare Free account. They are measurements of specific runs, not guarantees, and were not repeated on this commit. No Meta token and no Meta call was involved in them.

**Round 3 (deploy script, cron, wake, retention, storage):**
- Deployed with `scripts/cf-api-deploy.mjs` (full minified bundle incl. the meta-setup route, secrets from a mode-0600 file, workers.dev route, Cron schedule `* * * * *`); `verify` 6/6 pass from outside: GET / 200, handshake right token 200 + challenge, wrong token 403, meta-setup 404, unsigned POST 401, signed POST 200. URL shape confirmed: `https://<worker>.<account-subdomain>.workers.dev/api/webhook`. The `wrangler login --device` path (`scripts/deploy-cloudflare.sh`) was NOT run live (it needs the owner's interactive login).
- Cron Trigger fires: the first run came about 4 minutes after the schedule was created, then every minute; each run executed the wake-retry pass and the retention pass.
- Wake: a payload with IDs and counters only reached the receiving URL with `Authorization: Bearer <WAKE_KEY>` after the 1 s debounce (HTTP 200). A wake that failed (no URL configured, or a URL answering 404) was retried by the Cron pass after the backoff (~4 min after the 2nd failure) and delivered. A receiver on the same account's `workers.dev` failed with error 1042 until `global_fetch_strictly_public` was set. While the receiver failed, every further inbound message for that conversation attempted another wake (hundreds of attempts in a load run): expect wake POSTs per inbound message while your agent URL is down.
- Retention (conversations written with old timestamps through a test-only route): 40 replied conversations idle 20 days were trimmed to 10 messages, 20 idle 200 days were deleted, 10 fresh and 130 idle-but-pending ones were left alone; the SQLite file shrank 778,240 -> 450,560 bytes. A starvation bug found by this test (more than 100 untrimmable idle rows were re-read forever) is fixed: examined rows are marked and the next pass moves on (pass 1 examined 100, pass 2 examined 90, then 0).
- Storage growth with traffic (20 customers, 3,000 further POSTs): stored messages stopped at the per-conversation cap (50); total conversation JSON stopped growing once the 200-id dedupe ring filled; database size flat at ~0.7 MB.
- Durable Object analytics for the whole session (~3,300 webhooks, 3,000 loaded): 11,078 Durable Object requests (0 errors, wall p50 63 ms, p99 184 ms), 9,032 rows written, 46,356 rows read, DO CPU ~0.44 ms per request. 1 client timeout (30 s) in 3,000 posts at 10-way while wakes were failing in the background.

**Round 2, row-per-conversation store (current design):**
- Functional script: all 18 checks pass live (handshake right/wrong, unsigned/wrong signature, signed POST, duplicate, MCP list/claim/history/send_reply guards/finish, admin delete, meta-setup 404).
- Load, 10 concurrent signed POSTs from one machine, 40 customers (one conversation each), 300 POSTs per run, five runs (1,500 messages stored, ~1,600 incl. other traffic): 1,500 x 200, 0 x 503, 0 timeouts. Client latency p50 0.28-0.45 s, p95 0.54-0.55 s, p99 0.60-0.64 s (mostly network round trip from the test machine).
- Worker CPU per request (Cloudflare analytics, Worker only, per-minute buckets; p95 is not offered, p90/p99 are): small data p50 2.8 ms / p90 7.5 ms / p99 21 ms (first minute, includes cold starts); with ~1,000-1,500 stored messages p50 2.6 ms / p90 5.3 ms / p99 8.4 ms. Mean ~3.1 ms. **Flat as data grew** (whole-document design: median ~4 ms rising to 9-11 ms). Commit attempts per request: 1,769 of 1,789 needed one attempt, 20 needed two, none more.
- Worst case, 200 POSTs at concurrency 10 for the SAME conversation: 199 x 200, 1 x 503, client p95 ~4 s, max 8.5 s; commit attempts up to 16; Worker CPU p50 4.1 ms, p90 15 ms, p99 37 ms (retries cost CPU). Not a realistic pattern for one customer but it shows the limit.
- **CPU above 10 ms was not terminated** in these runs: every request with CPU over 10 ms (p99/p999 up to 42 ms) finished with status `success` and HTTP 200; no `exceededCpu` status appeared. That does not prove the limit is never enforced on Free plans; do not rely on it.
- Worker CPU only here; Durable Object CPU, requests and rows are in round 3.

**Round 1, whole-document store (replaced):**
- A bug the local tests missed, fixed: the group-commit queue was shared between requests, so concurrent webhooks were cancelled by the runtime as "hung" (HTTP 500, error 1101): 172 of 300 requests failed. The store is now created per request; a regression test (40 simultaneous POSTs) fails without the fix.
- After that fix, 300 POSTs at concurrency 10: 259 x 200, 40 x 503, 1 timeout, p95 ~8.7 s; CPU median ~4 ms rising to ~9-11 ms at ~1,000 messages. That was the reason for the row-per-conversation store.
