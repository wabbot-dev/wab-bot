# Self-provisioning secrets (no API token, no `wrangler login`, no dashboard step)

Some deploy paths cannot carry secret values: for example the Cloudflare MCP plugin redacts them to the literal text `[REDACTED]` (a Worker deployed that way would otherwise hold, and trust, the string `[REDACTED]`). Requiring every importer to create an API token or run `wrangler login` is a lot to ask, so the Worker can **receive its secrets itself, once**:

1. Deploy the Worker with **no secret bindings** and one plain-text (non-secret) var, `SETUP_NONCE`, a random value (>= 32 chars) that the deployer generated. `node scripts/cf-api-deploy.mjs init --secrets-file F --from-env` creates `F` (mode 0600) with a random nonce and the bridge's own tokens (and picks `WA_APP_SECRET` / `WA_ACCESS_TOKEN` and other managed names from the environment; `--map NAME=ENVVAR` renames); `deploy --self-provision --secrets-file F ...` uploads only the nonce (`--emit-plugin-js` for a tool that already holds a Cloudflare session). With an account that has older secret bindings of the same names add `--purge-secret-bindings` (a binding that survives a re-upload beats a stored value: found live).
2. `node scripts/cf-api-deploy.mjs provision --url <worker url> --secrets-file F` sends `POST /api/setup {nonce, secrets:{...}}` over HTTPS. Nothing is printed except the HTTP status and the stored **names**.
3. The Worker compares the nonce in constant time, validates every value **before** claiming (a typo does not burn the one chance), then claims setup with one atomic transaction inside the Durable Object's SQLite and writes the values there. From then on `POST /api/setup` answers **403** (`setup_locked` for the right nonce, `forbidden` otherwise), forever. There is no unlock call; to start over, tear the Worker down and deploy a new one. Setup must leave an `ADMIN_TOKEN` behind (in the body or as a binding), otherwise 400 and nothing is claimed.
4. Optional: redeploy with `--no-nonce` so the nonce var is gone from the Worker too (stored secrets survive a redeploy; the lock does not depend on the var).
5. Later changes, only with the admin token: `GET /api/admin/secrets` lists names and sources (`env` / `stored` / `unset`, never values); `POST /api/admin/secrets {secrets:{NAME:"new"|null}}` rotates or deletes (`ADMIN_TOKEN` cannot be deleted; rotating it needs the current one). CLI: `node scripts/cf-api-deploy.mjs rotate --url U --admin-token-file F --secrets-file G`. The instance that handled the change uses it at once; other running instances pick it up within 30 seconds.

Names that can be provisioned: secrets `WA_ACCESS_TOKEN`, `WA_APP_SECRET`, `WA_VERIFY_TOKEN`, `MCP_TOKEN`, `ADMIN_TOKEN`, `CRON_SECRET`, `WAKE_KEY`; settings `LAUNCH_MODE`, `TEST_RECIPIENTS`, `WA_PHONE_NUMBER_IDS`, `WA_TEMPLATE_ALLOWLIST`, `WAKE_URL`, `WAKE_HEADER`, `WAKE_AUTH`, `WAKE_DEBOUNCE_MS`, `WAKE_TYPES`, `GRAPH_VERSION`. **A real Worker binding / var of the same name always wins over a stored value** (so `LAUNCH_MODE=test` set as a var cannot be overridden to `live` from storage). Values are never logged, never echoed, never returned by any endpoint and are kept in their own SQLite tables (`secrets`, `setup`), apart from the conversation rows, so the admin console, retention and the MCP tools never touch them.

**Honest limits of storing secrets in Durable Object storage** (instead of Worker secret bindings):
- Cloudflare encrypts storage at rest, but this code adds **no** application-level encryption (there is no key the Worker could hold that the same code path could not also read). Anyone who can deploy code to the Worker, or who has dashboard / API access to the account and its Durable Object data, can read the values. A Worker secret binding is not readable back from the dashboard; a stored value is a weaker guarantee against a compromised Cloudflare login. The Cloudflare account is the trust boundary either way (whoever controls it can also deploy code that reads a binding).
- The nonce is a plain-text var: anyone who can read the Worker's settings before setup runs can claim setup. Generate it fresh, run `provision` right after `deploy`, and treat the window between the two as the exposure. After the claim the nonce is useless (and `--no-nonce` removes it). If someone else claimed first, you would see 403 `setup_locked` on your own call; in that case tear down and redeploy.
- Whoever calls `/api/setup` first with the nonce wins; there is no second factor. No rate limit on wrong nonces (a 192-bit random nonce is not guessable; every call is a plain 403).
- Durable Object storage has point-in-time recovery for up to 30 days, so a rotated-away value can persist in backups for that long (Cloudflare's feature, not controllable here).
- A lost `ADMIN_TOKEN` with no binding means no rotation path: the only reset is teardown and redeploy (which also deletes conversations).
- Each isolate asks the Durable Object for the stored values at most every 30 s (one extra Durable Object call, counted against the Free quota); if that call fails, the last known values keep being used.
- Not independently audited. Verified live on a test Worker only (see [STATUS.md](STATUS.md)).

**Webhook callback URL shape** (Meta's "Callback URL"): `https://<worker-name>.<your-account-subdomain>.workers.dev/api/webhook`, verify token = `WA_VERIFY_TOKEN`. The subdomain is per account (Workers & Pages > Subdomain).

Then: `bash scripts/smoke.sh https://<worker>.<your-subdomain>.workers.dev`, finish Meta setup ([docs/META-SETUP.md](META-SETUP.md)), connect the agent. Remove everything with `bash scripts/teardown-cloudflare.sh` (deletes the Worker and all stored conversations).

Safe defaults: `LAUNCH_MODE=test` (only exactly `live` sends to non-allowlisted recipients), auto-reply **paused** until an admin activates it, templates off until `WA_TEMPLATE_ALLOWLIST` is set, `/api/admin/meta-setup` **off** until `META_SETUP_ENABLED=1`.

`XAI_API_KEY` (voice calling) can be provisioned the same way. `ADMIN_MCP_TOKEN` and the calling gate (`CALLING_MODE`, `CALLING_BV_DONE`, `CALLING_GO_NUMBER`) deliberately cannot: they are Worker bindings you set yourself ([mcp.md](mcp.md), [VOICE-CALLS.md](VOICE-CALLS.md)). The SMS or voice code for your WhatsApp number is never part of provisioning: you enter it yourself in Meta's form and no tool here receives it.
