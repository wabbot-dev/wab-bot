# State store, retention and wake

State is one SQLite row per key inside one SQLite-backed Durable Object (`src/state-do.ts`): one row per conversation (`conv/<id>`), a few small rows for controls, rate-limit counters and rejection counters, and a global version counter. `lib/store.ts` keeps the `Store` interface (`snapshot({keys,prefixes})`, `commit(base, writes)`): a request loads only the rows it needs (reading an unloaded key is an error), and commits all its changes in ONE Durable Object call. The Durable Object is single-threaded: it checks that every row the request loaded or writes still has the version it saw and then applies all writes in one synchronous transaction, so the compare-and-swap is exact, and requests touching different conversations never conflict. Versions come from a global counter and are never reused (no ABA after delete/recreate). Updates issued together within one request are group-committed (never across requests: see src/runtime.ts); a lost race re-reads only the conflicting rows, re-applies the pure update function and retries with jittered backoff for ~8 s (max 25 attempts). A row above 1,000,000 characters is refused. Typical customer exchange: at most 5 successful writes (a test fails above that). Each read or commit is one Durable Object request.

Retention: `replied` conversations idle 14 days keep only the last 10 messages; **any** conversation idle 180 days is dropped; `DELETE /api/admin/conversations/<id>` (or the admin action `delete_conversation`) erases one immediately. Rows are compacted when written, so idle conversations are handled by a daily pass (Cron Trigger `0 5 * * *`, or `GET /api/cron/retry-wakes` with the cron secret) that examines up to 100 least-recently-written conversations per run (known limitation: many idle conversations that cannot be trimmed could crowd out others) and purges expired counters. Weakened versus a real database: one Durable Object serialises all writes, and a single conversation hit by many simultaneous webhooks serialises on its own row, so this suits single-tenant, small-business volumes only. Replay note: dedupe ids are kept per conversation (last 200) and cleared at the 14-day trim; Meta does not sign a timestamp, so a captured signed payload replayed after that could re-add a message.

## Wake / debounce
Debounce default 8 s anchored to the first message of a burst; only the invocation holding the wake's runner token fires it; no wake while claimed/escalated/taken over/held; wakes fire even when auto-reply is paused; failures back off `min(6 h, 60 s x 2^attempts)`; retries run opportunistically on webhook POSTs (once per 5 min per isolate) and on the daily Cron Trigger; activating auto-reply wakes every pending conversation. Payload: `{event, conversation_id, pending_messages, wake_at, note}`, IDs and counters only, never message text. The wake runs in `ctx.waitUntil` after the response (Cloudflare allows up to 30 s after the response, hence the 25 s debounce cap).
